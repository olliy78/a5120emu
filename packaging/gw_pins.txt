# Gepinnte Greaseweazle-Fassung — die Anbindung an ECHTE Diskettenlaufwerke.
#
# Warum eine eigene Pin-Datei und nicht requirements.lock:
#
# Die Greaseweazle-Hosttools liegen NICHT auf PyPI (Stand 2026-08-18: 404).  Es
# gibt sie nur am GitHub-Release — als Quellarchiv.  Ein Quellarchiv kann pip
# aber nicht einfach einspielen: `setup.py` erklaert eine C-Erweiterung
# (`greaseweazle.optimised`), und die muesste beim ANWENDER uebersetzt werden.
# Unter Windows hat er keinen Uebersetzer; die Installation braeche ab.
#
# Deshalb wird beim SCHNUEREN ein **wheel** daraus gebaut und dem Paket beigelegt
# (ein wheel, Endung `.whl`, ist das FERTIGE Installationsformat fuer
# Python-Pakete — ein ZIP aus den einspielbaren Dateien plus `*.dist-info`;
# der Gegensatz ist das Quellarchiv, das `pip` erst bauen muss)
# (packaging/build_payload.sh, `--refresh-gw` frischt die Pins auf).  Der
# Installer spielt es ohne Netz und ohne Uebersetzer ein; die vier
# Abhaengigkeiten (crcmod, bitarray, pyserial, requests) liegen dagegen sehr wohl
# auf PyPI und kommen mit Pruefsumme aus requirements.lock — sie werden also
# zusammen mit Qt geladen.
#
# Die C-Erweiterung entfaellt dabei BEWUSST.  Beide Stellen, die sie benutzen,
# haben einen Rueckfall in Python (`except AttributeError` in usb.py:487 und
# track.py:406); gemessen am 2026-08-18 kostet der Verzicht rund 25 ms je Spur,
# waehrend das Lesen einer Spur am echten Laufwerk 500–800 ms dauert.  Dafuer
# gibt es EIN wheel fuer alle Systeme (py3-none-any), keinen Uebersetzer beim
# Anwender und keine Bindung an die Python-Nebenversion.  Der Preis dafuer ist
# eine Warnzeile auf der Standardausgabe beim Import — die faengt
# app/gw/device.py ab (dort steht auch warum: die Ausgabe ist bei
# `k1520disktool --physical` die Nutzlast).

# share/doc/lizenzen/greaseweazle-COPYING.txt.
